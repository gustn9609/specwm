## 2. Positions stated

- **Guandao's framing of the project:** on-device interactive world models are unsolved; constraints on device → ask the cloud for help; speculative decoding is *one* way to collaborate, "not married to it". Spec decoding only pays if the teacher is very good AND cannot run on device; if the teacher runs where you are, just run the teacher. Expected latency is between draft and teacher, quality at most teacher.
- **Video ≠ text for spec decoding:** shown frames cannot be retracted. The drafter must run *faster than real time* so the teacher corrects frames not yet shown (work ahead). Variants: spec decoding in latent space (decode later); drafter predicts a jump-ahead future, teacher judges it, drafter fills in-between frames (interpolation is easier than physics); user-action changes react on device first, teacher verifies the consequence (analogy: interrupting an LLM — look for LLM work on interruptible spec decoding).
- **Teacher must also be fast:** when confident use the teacher's one-step x0 prediction; when the (PCA) trajectory departs, run the teacher for several steps. → our chunk-wise adaptive-steps head is exactly this knob; the departure detector would decide fast vs heavy correction.
- **Low resolution:** Guandao "always likes going lower res"; frame rate is tied to resolution. Below the training resolutions the model needs fine-tuning: roll out ODE pairs (noise → final latents) from the teacher and fine-tune the 14B at the lower resolution; needs a base model that has seen that resolution. Eventually must come back up to full resolution, so the upsampling cost must be shown.
- **Remove the VAE:** Guandao's teammate (Apple) has a forthcoming paper removing VAEs and the KV adapter; but Waypoint already uses a tiny VAE, so the VAE is probably not the biggest gap.
- **Diana on novelty:** techniques are mostly existing; the value is the *explanation*: formalize why the trajectory must stay near the target and connect that argument to the techniques; show where it generalizes and where it fails ("why does this hammer work on this nail"). Post-doc on the theory side can help.
- **Diana on "on-device":** PRO 6000 is not a device. 4090 / A5000 (24 GB) count; the more constrained the better; MacBook-class is probably impossible. Also profile **memory footprint and energy**, not only latency/throughput — her group has a profiling add-on (Bokun + Hongye) that reports latency, throughput, memory and energy; conclusions may change. Energy also motivates hybrid: a company offloads part of the energy cost to the user's device.
- **Guandao's "biggest risk":** can the 14B be stored and run on a device at all? "If we can, that is a strong first step." First action: check the peak memory of the 14B and whether quantization gets it on device.
