# Action item 1: Latency in world-model metrics (TTFF, steady fps, action→frame, plus the 10 s clip time)

**Headline:** All four latency metrics now exist for the teacher and for our quality and realtime modes, with one protocol (Chenfeng's method, jar + sandcastle, one RTX PRO 6000 GPU, full-VAE decode streamed on the same GPU; table e, figure f13_latency). Only generation is measured in these runs: TTFF and e2e add an assumed ≈ 2.0 s deployable prepare (README Q), not a prepare measured here. Generation only, quiet and steady (table f), the teacher runs at **4.08 fps**. Our modes run at **6.80 fps (teacher-parity, 1.67×)**, **9.74 fps (quality, 2.39×)** and **15.73 fps (realtime, 3.85×)**. Only the teacher-parity ratio is on the teacher's own chunk-to-chunk basis; the quality and realtime rates are cloud-step time (`cloud_chunk_s`), so those two ratios are not like-for-like (facts §12). The bench-43 under-load ratios (1.74× / 2.5× / 4.1×) agree within ~5 %. With the decode on the same GPU, ours realtime has the lowest action→frame latency of all baselines and operating modes (table e): p50 1296 ms vs teacher 3237 ms and student 1434 ms. Two unused reference variants (table f, not modes) are lower: 704 fused without partial commit (1180 ms, but 12 % boundary jumps) and 576 fused + partial (818 ms, at 304×560, lower quality). Ours realtime also gives 10.8 vs 4.2 output fps (both whole-clip means), TTFF ≈ 2.57 s vs 3.71 s, and a 10 s clip end to end in ≈ 16.6 s vs 40.2 s (the student, with its own 1.5 s prepare, takes 16.5 s; table e2). Quality mode gives 6.9 fps, p50 1995 ms, TTFF ≈ 2.85 s and ≈ 24.8 s per clip. On jar + sandcastle (hard prompts, few accepted chunks), SDVG is slower than target only at both thresholds with the same stack and measurement (optimized: 51.2 / 43.3 s vs 37.8 s per clip, p50 4463 / 4156 vs 3237 ms). On bench-43, τ −2.2 is faster than the teacher (6.7 vs 3.9 steady fps, under load) but costs −0.84 ± 0.10 quality (facts §2). No arm meets the 750 ms per-frame deadline; ours 704 misses it on 96.7 % of frames. Teacher-parity mode has no per-frame latency yet, because `spec_early` has no streaming decode. The often-quoted "teacher 4.9 fps quiet" is a whole-clip average; on the steady definition the teacher runs at 4.08 fps quiet (Caveats).

## What we report from now on (Guandao, 10/5)
- **Method:** Chenfeng's `sdv2_latency` (the StreamDiffusionV2 demo measurement), ported as `scripts/wm_latency.py`. For each config it writes per-frame `frames.csv` and `summary.json`, and it writes one `all_summary.json`. The KDE plot is not generated by this script; f13_latency draws it (`scripts/f13_latency.py`, same kernel as `sdv2_latency.gaussian_kde`).
- **TTFF ↓:** `first_frame_ms` is the time from generation start until the first decoded frame is in host memory. TTFF = ≈ 2.0 s deployable prepare (T5 on GPU + image encode, README Q) + first frame. The scripts' own `prepare_s` is not TTFF. It is 23–27 s in the profile (config means), because `spec_ar_loop` prepares both models with T5 on CPU. On bench-43 ours 704 it is 21.1 s (median), which includes the unused 1.3B device prepare. In the timing pass it is 4.4 s (ours 704) and 6.4 s (ours 832): cloud prepare only (`--no-device`), but with T5 on CPU (`res_split_infer` builds `V2Binding`, whose pipeline uses `t5_cpu=True`), so it is above the ≈ 2.0 s deployable prepare. TTFF and e2e therefore use the assumed ≈ 2.0 s (README Q), not a prepare measured in these runs.
- **Steady fps ↑:** 12 / the median chunk period over chunks ≥ 6 or chunks ≥ 5. A chunk is 12 video frames, or 0.75 s at 16 fps. This excludes chunk 0 (9 frames) and the KV-cache ramp. On bench-43 the median ours-704 cloud chunk rises from 0.536 s to 0.761 s over chunks 0–5, and the teacher's chunk period from 1.82 s to 3.04 s. The basis differs by source, and values on different bases are not comparable:
  - **Generation only** (bench-43 table a, quiet table f): `spec_early` arms (teacher, chunk-wise) use `chunk_start` with chunks ≥ 5; `res_split_infer` arms (ours) use `cloud_chunk_s` with chunks ≥ 6. No decode.
  - **Output, decode inside** (table e): per-frame ready times of each chunk's last frame, chunks ≥ 6, with the full-VAE decode streamed on the same GPU.
- **Mean output fps (whole clip) ↑:** `wm_latency.py` reports `fps` = (frames − 1) / (last ready − first ready). This includes chunk 0 and the ramp, so for the same run it reads higher than steady fps. We report it only under this name.
- **Action→frame latency ↓ (`server_ms`):** ready(frame) − request(its chunk). The request is the moment the chunk consumes its action. We report p50 / p90 / p99 and the miss rate above 750 ms (one chunk of real-time playback). The miss rate above 1000 ms is quoted only for ours 704 (91.5 %); `summary.json` `server_ms.miss_rate_1000ms` has it for every row. `summary.json` also has a jitter value, which we do not use.
- **10 s clip time ↓:** we give two numbers. (i) Generation s per clip (`gen_s`) excludes prepare. With streaming decode (table e) the decode runs inside generation. (ii) e2e = prepare + generation + final decode is the 10/5 metric. For example, SDVG on the original stack has generation 80.0 s and e2e 99.9 s. With streaming decode only a short decode tail remains after the last chunk (0.29 s at 704, 0.41–0.44 s at 832; means over clips, ours 832 0.42 s; table e2). A "10 s" clip is 13 chunks: 161 frames are requested and 153 are decoded (9 + 12 × 12), which is 9.6 s at 16 fps.
- All timings run on one NVIDIA RTX PRO 6000 Blackwell (96 GB), not an H100.

### Caveats
- **Teacher speed: use 4.08 fps quiet (steady), not 4.9.** facts.md §15 corrects this.
  - "4.9 fps quiet" is a **whole-clip average**: 153 frames / 31.2 s generation on the cmp10 prompts with seed 1234 (README N), i.e. gen 31.2 s / 13 chunks. It includes the cheap early chunks before the KV window fills.
  - On the steady definition used everywhere else, the teacher runs at **4.08 fps quiet** (2.939 s/chunk, table f) and **3.9 fps under load** (3.038 s/chunk, bench-43). The two are 3 % apart.
  - So 4.9 → 3.9 is not a load slowdown. Speed-ups computed from 4.9 understate ours. The bench-43 under-load ratios (1.74× / 2.5× / 4.1×) and the quiet steady ratios (1.67× / 2.39× / 3.85×) agree within ~5 %; prefer the quiet ones.
- **Load.** Bench-43 fps were measured under load (7 GPU jobs at once; facts.md puts the slowdown at ≈ 10–20 %). Tables (e), (e2) and (f) ran with no other generation jobs, but VLM judges ran on other GPUs of the same host.
- **Different fps definitions.** SDVG, MG2 and Waypoint fps in table (a), and MG2 / Waypoint in table (f), are whole-clip averages, not steady state. The output fps in table (e) is also a whole-clip mean, and it includes the full-VAE decode on the same GPU. The steady column of (e) includes the streamed decode too, so it is not comparable with generation-only steady fps (bench-43 or table f). Example: optimized target only is 3.155 s/chunk in (e), the teacher is 2.939 s/chunk in (f).
- **Decode and prepare.** Bench-43 fps and generation times exclude decode or overlap it. Tables (e) and (e2) include decode inside `gen_s` (streaming, same GPU) and exclude the script's prepare. TTFF and e2e use the ≈ 2.0 s deployable prepare (README Q; 1.5 s for the 1.3B alone, README N), not a prepare measured in these runs (the timing pass's own 4.4 / 6.4 s still runs T5 on CPU). MG2 and Waypoint include their own decoders, so the columns are not apples to apples. The bench-43 ours generation times also include an unused 1.3B device commit (≈ 1.45 s/clip); the timing pass does not (`--no-device`).
- **Ours rows are not the profile run.** Ours rows in (e) / (e2) come from the timing pass (5 clips), the teacher, student and SDVG rows from the profile (6 clips). Both use the same protocol and stack on the same prompts, but ran at different times. Ours decodes at 704 when it generates at 704, which helps ours realtime in every per-frame column (footnote 8).
- **Per-frame latency for the teacher-parity mode.** The chunk-wise arms (cw*) run through `spec_early`, which records only `chunk_start` and no streaming decode (with `--no-video`, no decode at all). Their per-frame columns need a streaming-decode run. Until then they get steady fps and gen s only, both without decode.
- **What `server_ms` leaves out.** `server_ms` starts when a chunk consumes its action. On top of it come the user's wait for the next chunk boundary (up to 0.75 s at 16 fps), output encoding, the network and the display, as in sdv2_latency.
- **Simulated device, different GPU.** The "device" is simulated on the same GPU, with no real network. A separate-device pipeline (decode off the cloud GPU) is composed, not measured end to end. The GPU is an RTX PRO 6000 Blackwell, not an H100: Matrix-Game 2.0's official 25 fps is on an H100 with compile, while our MG2 runs use no compile.
- **Prompt sets.** Tables (e), (e2) and (f) cover jar + castle only (2 hard prompts × 3 seeds). SDVG accepts few draft chunks there. The same seed accepts different numbers of chunks on the two stacks (τ −2.2, jar s4321: 4 vs 10), so the τ −2.2 stack ratio mixes stack speed with acceptance. The bench-43 SDVG 44.6 s (optimized stack, 43 prompts, generation only, decode excluded) and the (e) SDVG 51.2 s (2 hard prompts, decode streamed inside) use different prompts and accounting.
- **Quality is context only.** The VLM quality column is a context number only, because the quality prompt has not been validated against human ratings (the drift prompt is, AUROC 0.82).

### 발표 메모 (Korean)
- 10/5 피드백대로 지표를 TTFF / steady fps / action→frame latency + 10초 클립 시간(generation s와 e2e = prepare + generation + decode) 네 개로 바꿨음. 측정은 Chenfeng 코드(sdv2_latency)를 그대로 포팅한 wm_latency.py로 함. 단 wm_latency의 fps는 whole-clip 평균이라 steady fps(chunk ≥ 6)는 따로 계산함.
- 슬라이드 핵심 숫자(맨 위 표): generation-only, quiet, steady 기준 teacher 4.08 fps, ours teacher-parity 6.80 fps(1.67×), quality 9.74 fps(2.39×), realtime 15.73 fps(3.85×). bench-43 under-load 비율 1.74× / 2.5× / 4.1×와 ~5 % 이내로 일치하므로, 슬라이드에는 quiet 값을 씀. 단 teacher-parity만 teacher와 같은 chunk_start 기준(like-for-like)이고, quality/realtime은 cloud step 시간(cloud_chunk_s) 기준이라 엄밀히 같은 기준은 아님(facts §12).
- **4.9 정정:** teacher "4.9 fps quiet"는 whole-clip 평균(31.2 s / 13 chunk, KV window가 차기 전의 싼 chunk 포함)임. steady 기준 teacher는 quiet 4.08 / under load 3.9(3 % 차이). 그래서 "부하 때문에 4.9→3.9"라고 말하면 안 되고, 4.9로 speed-up을 계산하면 ours를 과소평가하게 됨.
- 한 GPU에서 decode까지 포함한 per-frame 측정(Chenfeng 방식, 표 e, 그림 f13_latency): ours realtime이 action→frame p50 1296 ms로, baseline과 operating mode 중 가장 낮음(teacher 3237, student 1434). 단 f13의 연한 행, 즉 mode가 아닌 variant 두 개는 더 낮음: 704 fused(partial 없음) 1180 ms(boundary jump 12 %), 576 fused + partial 818 ms(304×560 저해상도). output 10.8 fps vs teacher 4.2, TTFF ≈ 2.57 s vs 3.71 s, 10초 클립 e2e ≈ 16.6 s vs 40.2 s(2.42×). 단 TTFF와 e2e의 prepare는 실측이 아니라 가정값(14B 2.0 s, README Q)이고, student는 자기 prepare 1.5 s(README N)를 쓰면 e2e 16.5 s로 ours realtime보다 0.1 s 빠름. quality mode는 6.9 fps, p50 1995 ms, TTFF 2.85 s, e2e 24.8 s.
- 공정하게 말할 점: ours 704가 student보다 latency가 낮은 이유 중 일부는 704에서 decode가 더 싸기 때문임(426 vs 832의 631 ms/chunk). decode 없이 보면 student가 더 빠름(bench-43 17.2 vs 15.8 fps). 또 ours 행은 timing pass(5 clip, castle s1234는 cold compile이라 제외)이고 teacher/student/SDVG 행은 profile run(6 clip)이라 같은 프로토콜이지만 다른 run임.

- 750 ms deadline은 아무도 못 맞춤. ours 704도 miss 96.7 %(1000 ms 기준 91.5 %). 가장 가까운 건 576 fused + partial(p50 818 ms, miss 60 %)인데 품질이 떨어짐. server_ms에는 chunk 생성 + decode가 다 들어가서, 750 ms 안에 들어오려면 둘의 합이 한 chunk 재생 시간보다 짧아야 함.
- SDVG: jar + sandcastle(어려운 prompt, draft chunk가 적게 수락됨)에서는 같은 stack·같은 측정에서 두 τ 모두 target-only보다 느림. bench-43에서는 τ −2.2가 teacher보다 빠름(steady 6.7 vs 3.9 fps, under load) 대신 품질 −0.84 ± 0.10. optimized 기준 클립당 51.2 / 43.3 s vs 37.8 s, p50 4463 / 4156 ms vs 3237 ms, e2e 53.6 / 45.7 s vs 40.2 s. τ −2.2에서 SDVG가 이긴 클립은 stack마다 6개 중 1개뿐(original castle s1234 62.4 vs 70.1 s, optimized jar s4321 34.1 vs 38.2 s). 최적화가 14B를 1.88× 빠르게 하는 반면 1.3B는 1.29×뿐(FP8은 14B에만)이라 SDVG의 손익분기 acceptance가 더 올라감.
- prepare: TTFF는 first frame + ≈ 2.0 s(T5 GPU, README Q; 1.3B 단독은 1.5 s, README N). 가정값이고 이번 run에서 잰 값이 아님. 스크립트의 prepare_s(profile 23–27 s는 두 모델을 T5 CPU로 준비, timing pass ours 4.4 / 6.4 s는 cloud만이지만 T5 CPU)는 TTFF가 아님.
