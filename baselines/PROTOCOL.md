# Frozen baseline protocol (v1, 2026-10-16) — "their setting, our side slightly disadvantaged"

Purpose: build ONE fixed benchmark of external on-device world models in THEIR settings (their scenes, their native inputs, their native resolution,
their official stack), run ours on exactly the same (scene, control program) pairs under rules that never favour us, freeze everything under
`/home/hk28965/specwm/baselines/`, and from then on only re-run OUR arms (`baselines/run_ours.sh`) when the algorithm changes.

## 1. Fairness rules (apply to every baseline)
1. Baseline = official checkpoint + official inference stack (flash-attn / compile / their VAE) at its native resolution and native frame rate, on ONE RTX PRO 6000 (same GPU type as ours). Record ckpt id/commit, precision, attention backend, VAE, warm-up handling (§7 checklist of specwm/4090_search.txt).
2. Scenes = the baseline's OWN demo / starter images (its domain), plus the shared neutral set (our 12 a832 start images, no text when the baseline has no text input). Every model sees the same start image at the same aspect (image letterboxed/resized by each model's own loader; we feed ours the image already resized to the baseline's resolution).
3. Control = the same control PROGRAM (Section 2) for every model, encoded in each model's native input (held keys / constant mouse / camera path). Ours receives the program as a camera path (c2w per frame). When a magnitude must be calibrated (mouse units per degree, keyboard speed), calibrate it on the BASELINE's own outputs (DA3 pose recovery of its videos), never on ours.
4. Resolution: ours runs at the baseline's resolution (max_area = its pixel count, image at its aspect) — including when that is above our native 832×480 (slower for us = allowed). Never the other way round.
5. Text: when the baseline takes no text, ours runs with an EMPTY prompt on that baseline's scenes (primary number). A second arm with a one-line generic caption is allowed but reported separately.
6. Clip = 10 s of video per (scene, program) at the model's native fps (ours 16 fps = 161 frames; Waypoint 4 frames/call; MG2 own fps; ABot 12 fps), seed fixed (1234), one clip per pair. TTFF and steady fps measured per the §7 checklist: generation only AND end-to-end incl. decode, both reported; warm-up clip excluded; peak VRAM allocated/reserved; T5/text-encoder residency stated.
7. Metrics on every clip: Qwen3-VL judge (quality 1–10 ↑, drift 0–100 ↓; `scripts/vlm_clip_score.py`), VBench 6-dim Quality Score + MUSIQ drift (`scripts/vbench6.py`), RPE Rot vs the program's commanded trajectory (`scripts/rpe_da3.py`; the commanded c2w of the program is the reference for EVERY model, keyboard ones included), and the §7 reaction test on program P5 (frames until the motion reverses after the input flip, from optical flow).
8. Ours = the single-GPU FP8 port (official LingBot fast inference needs 8 GPUs; our port is slower than official, i.e. a disadvantage we accept). Arms: teacher 4-step, rt2 (2-step), adapt25 (step-1 head + chunk-wise 3rd step), and the 1.3B 4-step student; plus Speculative Forcing on the 14B (sf24, token-wise ε 0.24) as the strongest same-model competitor. KV window 18 latent frames, 12 at ABot's resolution (1280×704: window 18 does not fit in 96 GB; `run_ours.sh`). Clip length: ours generates 165 frames (42 latent frames = 14 chunks of 3; the loader rounds the latent count down to a multiple of 3, so the 161-frame program alone would give 39 latents = 153 frames) from 165 poses (`programs/<P>.npz` key `c2w_165`, `make_tasks.py --frames 165`) and the clip is trimmed to its first 161 frames (10 s) before the metrics. [10/17 C] Headline hybrid arm `adapt25c1hyb` (`run_ours.sh SET adapt25c1hyb G`, tier-4 queue chunks) runs on a GPU PAIR (0+1, 2+3, 4+5: cloud on the lower, device on the higher index, both locks taken in ascending order): device = adapt25 on every chunk, every chunk sent to a cloud 14B FP8 that finishes it with one step at t=750 and feeds it back into the device KV, frozen as two streams of the same run, `runs/ours_adapt25c1hyb_dev_<SET>` (what the device shows) and `runs/ours_adapt25c1hyb_cloud_<SET>` (the cloud-final stream), with 2 GPUs recorded and ttff/e2e null (no streamed decode in the two-process mode).
9. Baselines also include Speculative Forcing in ITS setting: the LingBot 1.3B causal-fast with the training-free verifier (their published thresholds τ_red 0.375, τ_stab 0.300, ε 0.24) and, if a head can be trained in time, the learned verifier.
10. Nothing in `baselines/` is edited after the freeze except `runs/ours_*` (re-generated by `run_ours.sh`) and `metrics/` (append-only JSONs).

## 2. Control programs (10 s = 160 steps at 16 fps; piecewise-constant so every model's native input is a held key / constant mouse)
Units: yaw/pitch in degrees per second (positive yaw = a pan to the RIGHT: `yaw = atan2(Rr[0,2], Rr[2,2])` with `Rr = R_i^T R_{i+1}` on OpenCV c2w turns the forward axis toward camera +x; ABot key L = camera right, Waypoint +mouse-x, MG2 +mouse-yaw; all four baseline P2 smoke clips (Waypoint, MG2, ABot, Astra) pan right; positive pitch = camera up, key I); translation in "speed units" u/s in the camera frame (z forward); ours normalises translation per video, so only the shape matters for ours; for keyboard models a held W/S/A/D key IS the speed.

| id | name | 0–2.5 s | 2.5–5 s | 5–7.5 s | 7.5–10 s | tests |
|---|---|---|---|---|---|---|
| P1 | forward | fwd 1 u/s | fwd | fwd | fwd | look-ahead consistency, scale drift |
| P2 | turn | yaw +18°/s (right) | yaw +18 | yaw +18 | yaw +18 | 180° pan: revisit / parallax, look-back at the end |
| P3 | forward+turn | fwd 1 + yaw +12 | same | same | same | combined motion |
| P4 | S-curve | fwd 1 + yaw +18 | fwd 1 + yaw −18 | fwd 1 + yaw −18 | fwd 1 + yaw +18 | input flips (2 reversals), state persistence |
| P5 | stop-and-go | fwd 1 | still | back 1 (S) | fwd 1 | sudden input change → reaction frames; look-back (returns to the start) |
| P2p | turn-16 | yaw +16°/s (right) | yaw +16 | yaw +16 | yaw +16 | P2 at the largest MG2-unsaturated rate (its mouse cap 0.1 = 17.0°/s at K 0.0704): 160° pan, no saturation for any model |
| P4p | S-curve-16 | fwd 1 + yaw +16 | fwd 1 + yaw −16 | fwd 1 + yaw −16 | fwd 1 + yaw +16 | P4 (2 reversals) without MG2 mouse saturation |

Encodings (write `baselines/convert.py`: `program_to_c2w(pid, fps, n_frames)`, `encode_waypoint(c2w)`, `encode_mg2(c2w)`, `encode_abot(c2w)`, `encode_astra(c2w)`; reuse the rules of tools/waypoint/poses_to_actions.py, tools/mg2/poses_to_cond.py, tools/abot/poses_to_keys.py but take a pose array; calibrated constants live in `baselines/calib.json` with the measurement that produced them):
- ours / Astra / MG3.5: c2w per frame (OpenCV camera: x right, y down, z forward); intrinsics for ours follow the existing bench tasks: per-frame [416, 416, 416, 240] at the 832×480 reference frame (90° horizontal FOV; binding_v2 rescales to the output size) — `baselines/make_tasks.py` writes them; other models get their own default intrinsics.
- Waypoint: per 4-frame call `{mouse:[K_yaw·Δyaw, K_yaw·Δpitch], buttons:[W|S|A|D]}`; K_yaw = 68 units/deg/call (10/17 FINAL: proportional least-squares fit total_yaw = c·mouse_units over eight 10-s P2 clips of highland_castle_loch at 64–95 units/call, seeds 1234/1235, DA3 pose recovery `baselines/waypoint/calib_yaw.py` → `waypoint/smoke/calib_da3.json`, fit `waypoint/smoke/kyaw_fit.json`: c = 2.214 deg/unit → K = 150/c = 67.8 → 68; the realised turn at a fixed input varies ±6 % rms between seeds and processes (residual 11 deg), so K is a fit, not a one-clip value, and the expected P2 pan at K 68 is 181 ± 11 deg; the direct clips bracket it: K 66 → 161/168 deg, K 69 → 203/176, K 79 → 220/207 — the 10/16 one-clip value 79 over-rotated; the 10/9 flow value 118 came from a runner that re-appended the start image every call). P2 = 81.6 units/call, P2p 72.6, P3 54.4.
- Matrix-Game 2.0: per frame keyboard one-hot [fwd, back, left, right] + mouse [pitch, yaw] = K·deg/frame, K = 0.0704/deg/frame (10/16 DA3 on MG2's own P2 clip, `baselines/mg2/smoke/calib_P2_universal_0000.json`; the 10/9 flow value 0.067 stays in calib.json as `K_flow_1009`), clipped ±0.1 → 18°/s (P2, P4) saturates on every moving frame (largest unsaturated rate 17.0°/s): the saturation is reported in timing.json and P2p/P4p (16°/s) are run for all models. 129 frames are generated (frames % 4 == 1, latents % 3 == 0) and the first 120 (10 s at 12 fps) written.
- ABot: per block 8-key multi-hot [W,A,S,D,I,J,K,L] (J/L = camera left/right); block 0 = 9 decoded frames (start image + 2 latent frames), then 12 per block: 11 blocks = 129 frames generated, first 120 (10 s at 12 fps) written; a block straddling a 2.5 s switch takes its net motion, so ABot's input switches at decoded frames 33/57/93 = 2.75/4.75/7.75 s (`calib.json['abot']`).
- Astra: 20 fps, 201 frames kept (56 latents generated in 7 blocks of 8, cut to 201); per-latent relative 3×4 pose in its `sekai` format (`baselines/astra/program_to_astra.py`; the embedding handed to the official sliding window covers all 225 generated frames = 57 rows, `astra_gen.py build(pid, 20, 225)`; `programs/<P>.npz` keeps the first 51 = the 10 s program), rotation exact, 1 u/s = its preset forward speed 0.03 per latent (0.15 units/s). Translation VERIFIED 10/17 by DA3 pose recovery of Astra's OWN outputs (`astra/calib_astra.json` → `calib.json['astra']`): 1 Astra unit ≈ 7.3 m, the preset forward = 1.1 m/s walking speed on P1; under combined motion (P3) Astra suppresses translation whatever the scale, so u_scale 0.15 (its own operating point, rule 3) is kept; rotation rate exact while the view is faithful (18.2 deg/s for 18 on P2's first 2.5 s), 1.5–1.9× once the content is hallucinated — scored as drift (RPE Rot), not re-calibrated.

## 5. GPU discipline
The GPU is **assigned by the orchestrator** per round (10/17: GPU 4 only); every GPU job runs as `flock /tmp/gpu<N>.lock env CUDA_VISIBLE_DEVICES=<N> <cmd>` on that GPU, holds the lock < 20 min (batch jobs are split into chunk jsons sized for that, skipping clips whose `timing.json` exists) and records its peak VRAM; no other GPU is touched without an assignment (GPUs 0–3, 5–7 belong to other chains / the judge). Never kill processes you did not start. Absolute paths everywhere; run Python through `/home/hk28965/specwm/scripts/envrun.sh python` (main env) or the baseline's own venv.

## 7. [10/19] EXP 2 light device: `rt2c1hyb32` (additive; every other arm unchanged)
- **Arm:** `rt2c1hyb` with a 32-GiB device. Only the DEVICE process changes: `two_machine --window 12 --kv fp8 --cap 32 --lowmem 1` (run_ours.sh `rt2c1hyb32`, appended after the shared flags). The cloud is exactly rt2c1hyb's (FP8 weights, bf16 KV, window 18; 12 at 1280×704; no cap). Frozen streams `runs/ours_rt2c1hyb32_{dev,cloud}_<SET>`; the dev conversion records `kv_window` 12.
- **Options (two_machine, default off; the default path was checked bitwise on the deterministic harness `--compile 0 --timed-decode 0`: old vs new code, identical lat.pt + spec.mp4 md5):** `--kv fp8` = the self-attention KV ring buffer is allocated as float8_e4m3fn (= fit24 `--kv fp8`). `--cap G` = `torch.cuda.set_per_process_memory_fraction(G GiB / total)`; an allocation above it raises OOM, so the run fails when the configuration does not fit (`<out>/oom.json` records the stage and the peaks). `--lowmem 1` = (a) the bf16 DiT stays on the CPU and is FP8-quantized one block at a time on the GPU, so the 34.5-GiB bf16 checkpoint never sits on the GPU and the cap holds from process start (the weights are the same: `--lowmem 1` gave lat.pt and spec.mp4 identical to the default path on that harness); (b) the previous clip's KV is dropped before prepare; (c) spec.mp4 is decoded one latent frame at a time with the KV window still resident, which is what a streaming device holds. The device timing.json gets `mem` (torch peaks for load / warm-up / each clip's generation and decode, process peak, nvidia-smi process peak polled every 0.5 s); ours_to_timing copies it to `device_*` fields in both streams.

- **[10/19 PM v2: device decode in bf16, 2×2 tiles; supersedes the fit and queue lines above]** The arm's device also gets `--vae-dtype bf16 --vae-tiles 2,2`. The KV window stays resident during the decode. prepare's VAE encode keeps the fp32 model, and the cloud's decode is unchanged. Every rt2c1hyb32 set uses this one setting. On the deterministic harness the default path is again bitwise identical: lat.pt and spec.mp4 md5 match the original code.

## 9. [10/19 thesis] Memory-squeeze matrix on 60-s rollouts: device squeezes vs. cloud re-anchoring (additive; nothing above changes)
- **Thesis.** A memory-squeezed on-device world model (small KV window, FP8 KV, 4-bit weights, 2 denoising steps) drifts over 60-s rollouts; a full-context cloud that re-anchors the device KV (one 14B FP8 step at the last node, σ 0.625, fed back into the device KV = the rt2c1hyb mechanics) repairs it. Everything is measured on the P6 60-s sets `neutral_832_long` (832×480) and `mg2_long` (640×352), 4 scenes each (`tasks/<set>_long.json`, 969 poses → 961 frames; the same scorers as §6 incl. `vlm_seg` drift-over-time), against the tier-6 references on the same clips (teacher / rt2 / rt2c1hyb ...).
- **Matrix** (`run_ours.sh mx_flags`; every device runs the rt2 schedule nodes 0,500 --use 0,1; `mx<X>` = device only, `two_machine --role solo`, frozen `runs/ours_mx<X>_<set>`; `mx<X>c1hyb` = the same device flags + the standard cloud `--nodes 0,250,500,750 --use 3 --max-lag 99`, `--thr 0` on the device, frozen `runs/ours_mx<X>c1hyb_{dev,cloud}_<set>`; `ours_to_timing.py` records the device window / wq / mem fields in both; `report.py` treats them as any arm):
